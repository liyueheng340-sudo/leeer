# XAU 黄金分析系统 —— 现状总结与难点/卡点简报

> 用途：本文档用于把当前系统完整地带给外部模型进行讨论。
> 标注约定：【事实】= 代码/数据/文档直接支持；【推断】= 合理延伸但未验证；【候选假设】= 未验证想法。
> 读者不需要访问代码库，本文自包含。

---

## 一、系统是什么（一句话）

**XAU 黄金分析控制台**：一个只读的"军师"系统——从 MT5 终端取黄金（XAUUSD）实时行情快照，汇聚多层事实（报价结构 / tick 传感器 / 财经事件日历 / FRED 宏观 / EA 风控状态），交给 Qwen 大模型生成**中文交易简报**（方向、入场区间、止损止盈、风险标注），供交易者人工决策。

- 底层是开源框架 TradingAgents（TauricResearch，多智能体 LLM 交易框架，LangGraph）v0.3.1 的本地分叉。
- **双层结构纪律**：上游框架目录 `tradingagents/`、`cli/` 保持纯净；本地全部定制在 `local_console/` + `scripts/`。
- **无交易权限**：系统不下单、不持仓、不碰账户，只是分析。执行层另有 Cerberus EA（MQL5，demo 实盘）独立运行。
- 运行环境：Windows，本机 HTTP 服务（127.0.0.1:8767），浏览器界面。

## 二、架构现状（事实）

### 2.1 流水线（五阶段状态机）

```
QUEUED → SNAPSHOT → GATE → MODEL → VALIDATE → {COMPLETE, REJECTED, FAILED}
```

- `server.py`（HTTP）→ `service.py`（单 worker 线程池）→ `jobs.py`（状态机 + JSON 原子落盘）。
- 任务持久化在 `data_cache/xau_analysis_console/jobs/`，前端轮询恢复进度，刷新页面不丢任务。
- 两种任务：**brief**（快简报，quick 模型）与 **deep_review**（深度复盘，deep 模型）。

### 2.2 事实层（全部失败安全：传感器故障只降级、不阻断）

| 层 | 来源 | 用途 |
|---|---|---|
| MT5 快照 | 合并采集脚本（单 MT5 会话出报价 + tick 健康） | 第一事实来源：bid/ask、ATR、多周期结构 |
| tick 传感器 | 同会话零成本产出 | 点差峰值 ≥0.5、报价停滞 → 风险标注 |
| 事件日历 | ForexFactory 周历（人工周更 或 可选 URL 自动拉取） | 高影响事件窗口 → 风险标注 |
| FRED 宏观 | DFII10 / DTWEXBGS / DGS10 / T10YIE（6h 缓存） | 中期背景层，禁用于盘中价位描述 |
| EA 风控态 | 只读 Cerberus `ng_status.json`（30s 写一次，>120s 视为陈旧） | `PAUSED_NEWS` / `PAUSED_VOLATILITY` / `regime_blocked` / `hour.blocked` → 风险标注 |

### 2.3 闸门（2026-08-01 起"军师模式"，见系统宪法）

- `BLOCKED`：唯一保底——第一手数据不可用（快照过期 / 报价无效 / 身份不匹配）→ 模型不运行。
- `ANALYSE`：常态。**一切**风险因素（事件窗口、点差、波动、震荡市、EA 风控、共振相悖）都转成 `warnings` 风险标注随报告呈现，**绝不阻断分析**。
- 旧设计"事件窗口禁模型（WAIT）/ 降级禁方向（WATCH）"已废除——宪法判定那是"保安思维"，军师必须永远开口、永远给方向（没把握就明说没把握）。
- `REJECTED`：模型报告违反真实性/格式约束（引用不存在的数据、字段缺失、几何/幅度越界、非中文正文）→ 拒绝并重跑，不终止。

### 2.4 报告验收规则（validator，防幻觉核心）

- 来源白名单：模型只能引用事实包内真实存在的字段（`evidence_fields` 1-12 个，不存在即 REJECTED）。
- 正文必须中文（只允许白名单英文缩写 TP/SL/ATR/XAUUSD/DXY/FOMC/CPI/NFP/PCE/M5/M15/H1/H4）。
- 交易几何校验：多空方向 vs 入场/止盈/止损位置一致性；幅度约束（入场偏离 bid ≤ 3×ATR，TP ≤ 5×ATR，SL ≤ 3×ATR）。
- 方向纪律（共振相悖、震荡市强方向、入场不贴关键价位）已降级为 `validation_warnings` 风险标注——报告照常验收，风险如实呈现。

### 2.5 模型与性能（事实）

- 模型：quick = `qwen3.7-max`，deep = `qwen3.8-max-preview`（DashScope）。
- **MODEL 阶段占总耗时约 97%**：brief P50 38.9s / P90 66.3s；deep P50 86.4s，180s 超时失败率 3/8（37.5%）。
- 非模型路径（快照+闸门+校验）合计约 1.3s，已无可压缩空间。
- 真实 prompt 约 5.1KB（含全部六层约 9.2KB），不是瓶颈。
- 测试基线：`tests/local_console` **203 passed**。

### 2.6 已实证 NO-GO（踩过坑，不再做）

- 该经纪商 XAUUSD **DOM 深度档位全空** → 不能用盘口深度。
- StockTwits/Reddit 对黄金的软情绪覆盖太弱 → 不能做情绪层。
- 用 LLM 替代 FRED 宏观事实源 → 违反"先验证后分析"纪律，否决。
- 盘中引入 DXY/白银联动数据源进闸门 → 可靠性未验证，最多做背景层候选。

## 四、难点（已认知的硬问题）

### 难点 1：模型延迟是唯一瓶颈，但换不动
- 40–90 秒的单次分析延迟，对黄金 M1/M15 节奏的实战参考价值有限（等简报出来行情已经走了）。
- 瓶颈 97% 在模型本身。降速杠杆选项：换更快模型（无数据证明不降质）、流式输出（只改善感知速度）、超时放宽（180s→240s，但 worker 阻塞更久）。
- **没有第三方案，也没有验证"快模型质量"的手段**——这是一个速度/质量/成本三角僵局。

### 难点 2：幻觉防护 vs 军师"永远开口"的张力
- 防幻觉靠严格 validator（证据链 + 几何校验 + 中文契约），这是系统核心不变量。
- 但军师模式要求"任何时候都给方向"，两者冲突时容易滑向两个极端：validator 过严 → 高 REJECTED 率（历史 6.8%，全部因中文字段违规）；validator 过松 → 幻觉漏进报告。
- 目前靠"warnings 分级呈现"缓冲，但**"哪些纪律该硬校验、哪些该降级为标注"的边界是手工拍的**，没有系统化方法。

### 难点 3：Windows 平台稳定性（已踩坑修复，但心有余悸）
- 曾发生"任务卡 QUEUED 零痕迹"事故：`os.replace` 被 Defender/索引器瞬时占用 → PermissionError → 异常被线程池静默吞掉。三层修复：写盘退避重试、future 回调落日志、禁端口复用。
- 这类"外部进程干扰 + 静默异常"问题在 Windows 上难以穷尽，是长期运维负担。

### 难点 4：测量层纪律 —— 无法快速证明"系统有没有用"
- 复盘统计（TP_FIRST/SL_FIRST、胜率、按模式分组）**明确不构成 edge 证据**（无对照、样本少、无因果验证）。
- 52 个历史任务，brief 只有 44 个有效样本；deep_review 只有 8 个。要验证"scalp vs swing 哪个有 edge"、"IV 层有没有用"，样本积累速度太慢（一天可能就几个任务）。
- **系统在"功能正确"和"交易有效"之间存在巨大的验证鸿沟**，目前只有前者被证明。

### 难点 5：事实层的"位置感"缺失
- 模型有价格/ATR/结构数据，但**没有前日高低、周高低、摆动点、整数关口、交易时段上下文、点差历史分位**这些"位置感"信息。
- 已识别为 A1/A2/A3 增强项（纯确定性计算、零模型成本），但未落地。
- 推断：缺少位置感可能导致模型给"悬空档位"（入场不贴关键价位），目前只能靠 validator 事后标注。

### 难点 6：双系统数据源重复（控制台 vs EA）
- 控制台拉 ForexFactory 周历 `.xml`，Cerberus EA 拉同源的 `.json` 缓存——**同一发布方、两个端点、两份缓存**。
- 已落地"接口 B"（EA 风控态 → 控制台风险标注），但"接口 A 日历单源"未做，语义冲突风险仍存在（控制台说"可分析"而 EA 因新闻窗口停机的情况理论上可能出现，目前靠双方同源日历缓解）。

## 六、想和外部模型讨论的问题

### A. 延迟与架构
1. 40–90s 的 LLM 分析延迟，在黄金 M1/M15 实战里怎么破？除了"换模型/放宽超时/流式"还有没有别的思路（比如任务分层：秒级规则层 + 分钟级 LLM 层；或并行多档分析）？
2. 单 worker 串行队列是瓶颈吗？并发多个 brief 任务 vs 保持单 worker 的一致性和资源可控，怎么权衡？

### B. 军师模式与风险
3. "分析层永不锁死、只有数据不可用才 BLOCKED"这个宪法，从风险管理角度是站得住的吗？"永远给方向"和"没把握明说没把握"之间，实际执行时模型会不会系统性地过度自信？
4. "哪些纪律硬校验、哪些降级为标注"的边界目前是手工拍的——有没有系统化的划分方法（比如按"可验证性 × 对交易的危害"两个轴）？

### C. 验证与测量
5. 只有 44–52 个样本、无对照组的复盘数据，要验证"scalp vs swing 哪个有 edge"最少需要什么样的实验设计？有没有低成本的自举/模拟方案（比如用历史数据回放生成伪实时样本）？
6. 防幻觉 validator（证据链 + 几何校验）会不会扼杀模型的表达空间？有没有"宽松生成 + 严格标注"的更优组合？

### D. 系统边界
7. 分析层（军师）与执行层（EA）目前解耦。如果最终目标是"军师的分析能帮 EA 调参/暂停"，接口应该怎么设计才不违反"分析层不锁执行层"？
8. 上游 TradingAgents 框架的"故障容错"改动（try/except 降级）该保留还是回退？保留的话如何维护"上游纯净"的升级纪律？
